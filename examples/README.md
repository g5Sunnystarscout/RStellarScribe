# Example: 钒代镁铁碳基类 (Vanadic Organisms)

A real, loadable Stellaris mod that adds a **new species class** — a peer of the vanilla
Humanoid / Plantoid / Lithoid entries — written with RStellarScribe's tools and verified by
launching the game and looking at it in the empire creator.

## Install location matters more than anything else here

**The game does not mount a local mod whose folder path contains non-ASCII characters.**
It still parses the `.mod` descriptor (so the engine will happily report an invalid
`supported_version` for it) and it reports **nothing** in `error.log` — the content simply
never loads. On a Windows account with a non-Latin name this breaks every local mod placed
in `Documents\Paradox Interactive\Stellaris\mod\`, because the user path itself is non-ASCII.

Verified by isolation on Stellaris 4.4.6, with everything else held constant:

| Mod content at | Duplicate-key probe in `error.log` | Loaded? |
| :--- | :--- | :--- |
| `<mods>\vanadic_species` | `... already exists, using the one at file: common/map_modes/zz_zz_mount_probe.txt` | yes |
| `C:\Users\<non-ASCII>\Documents\Paradox Interactive\Stellaris\mod\vanadic_species` | nothing | **no** |

So the layout that works is: **content on an ASCII path**, and only the tiny launcher
descriptor in the Documents mod folder:

```
<mods>\vanadic_species\        <- all the content
C:\Users\<you>\Documents\Paradox Interactive\Stellaris\mod\vanadic_species.mod
                                         <- 8 lines, with path="<mods>/vanadic_species"
```

`vanadic_species.mod.launcher` in this folder is that descriptor, kept for reference.

RStellarScribe now flags this: `validate_stellaris_project` fails a non-ASCII mod root as a
hard error, a write to such a root returns `mount_warnings`, and `validate_stellaris_debug_run`
reports a `MOUNT BLOCKER`.

The biology: this species replaces the magnesium and iron centres of its
metal-requiring proteins with **vanadium**. Vanadium nitrogenase fixes nitrogen without
high-pressure chemistry, and vanadium's many oxidation states move electrons efficiently
at ambient temperature, but a vanadium centre assembles more slowly than an iron-sulfur
cluster.

## Files, and why each one is needed

| File | Purpose |
| :--- | :--- |
| `descriptor.mod` | Mod metadata. Generated by `generate_stellaris_mod_descriptor`. |
| `common/species_classes/zz_vanadic_species_classes.txt` | The class itself. Its `trait = "trait_vanadic"` line is what grants the trait to every species of the class — the same mechanism vanilla uses for `LITHOID = { trait = "trait_lithoid" }`. |
| `common/traits/zz_vanadic_traits.txt` | The granted trait, with the four modifiers that express the biology. |
| `common/portrait_sets/zz_vanadic_portrait_sets.txt` | **Required for the class to be selectable.** In 4.1.7+ a species class gets its portraits from `common/portrait_sets/`, not from `custom_portraits` (which has 0 occurrences in the shipped files). |
| `common/portrait_categories/zz_vanadic_portrait_categories.txt` | Groups the set into a category in the empire creator, labelled with the class key. |
| `localisation/<language>/vanadic_l_<language>.yml` | `vanadic` (class name), `trait_vanadic` and `trait_vanadic_desc`. UTF-8 **with** BOM, written by `generate_localisation_batch`. |

The launcher-side `<name>.mod` file lives in `Documents/Paradox Interactive/Stellaris/mod/`,
outside the mod root, with an extra `path=` field. RStellarScribe never writes outside
`output_root`, so it returns that file's content instead; it was placed by hand here.

## Note the naming

Every file uses a `zz_vanadic_` / `vanadic` prefix. Vanilla files start with `00_`, and
whether a same-named file merges with or replaces a vanilla one depends on per-directory
rules; a distinct prefix avoids the question entirely.

## Verification performed

- `validate_stellaris_project` → **green, 0 errors, 0 warnings**, with `game_root` pointed
  at the actual installed game.
- `validate_stellaris_localisation` → 0 errors, BOM and language headers confirmed byte-wise.
- The engine itself was made to name the mod: with a deliberately invalid
  `supported_version`, `error.log` reported
  `Invalid supported_version in file: mod/vanadic_species.mod line: 7`, proving the mod is
  in the loaded set.
- A normal run's `error.log` contains **no** line mentioning this mod, and
  `classify_error_log` attributed none of the 43 error lines to its files.

## What a species class does *not* need

- No `<key>_desc` localisation: vanilla species classes have none (0 occurrences in
  4.1.7), so the tool no longer invents one.
- No `common/leader_traits/`, no `common/species_names/` entry, no event.
- No new art: the portrait set reuses shipped portraits. Lithoid portraits are DLC-gated in
  vanilla, so they are mirrored here behind `has_lithoids = yes`, with base-game arthropoid
  and molluscoid portraits as the unconditional selection.
